# Planning with GitHub sub-issues as tasks

Sub-issues are tasks for **independently trackable deliverables**, not a mandatory format for every technical step. First inspect the project's existing issue structure and assess fit using `discovery.md` and `planning.md`.

- Keep the parent focused on shared outcome, boundaries, and project-level risks; each child has one bounded result, scope, verifiable acceptance criteria, validation evidence, and only genuine prerequisites.
- Use a checklist inside one issue for sequential steps of a coherent deliverable. Create sub-issues when distinct progress, ownership, acceptance, or lifecycle tracking is valuable. Independent outcomes should not be forced under a parent.
- Parent/child grouping is organizational, not a blocker or proof of completion. Add native blocking edges only for concrete prerequisites and verify them; explain rationale in the plan.
- Detail only the next executable tasks. Leave later work at outcome/decision level when findings may change it. Keep unresolved material decisions visible; a task with a safety- or scope-critical unknown is not implementation-ready.
- Each task should state outcome, included/excluded scope, dependencies, acceptance criteria, validation, and material risks/decisions. Avoid duplicate obligations between parent and children.
- Creating, linking, splitting, or migrating GitHub issues requires explicit authorization and the safe write protocol in `planning.md`/`shared.md`.
